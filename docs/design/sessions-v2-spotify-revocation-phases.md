## Closed internal API

```js
const handle = await prepareSpotifyRevocationInTransaction(
  tx, selector, reason = 'ownerRevoked', now = Date.now()
);
// Caller takes its predeclared lower lock categories and negative checks.
const cleanupIDs = await persistSpotifyRevocationInTransaction(tx, handle);
```

Both functions use the exact query-client object already passed to the actual SQL transaction. The handle is frozen with a null prototype and no properties or symbols; a module-private WeakMap holds all planned data. Spreading, JSON round trips and lookalike objects cannot reconstruct it. No connection image, digest, token, timestamp, callback or SQL is exposed on the handle. It is not an auth or privacy permit.

Preparation snapshots `ownerID`, `keyID` and `credentialDigest` synchronously before its first await. Each is a string or null/undefined. The existing selector remains the conjunction of these three nullable predicates; `{}` retains the trusted legacy all-connections meaning. Unknown own fields, arrays, mutable/object values, non-string reasons and non-safe-integer millisecond values refuse. All actual pinned caller shapes and reason strings remain supported. There is no new selector role or request input. The reason and millisecond value are primitives captured before awaiting. `Date.now()` remains the existing default for connection closure/consumer cleanup timing; it supplies no auth, freshness, deadline or privacy authority.

The first SQL samples actual `pg_current_xact_id()::text` and actual `to_regclass('spotify_connections')` presence. If present, preparation selects the matching physical connection IDs, ownership/enrollment columns, exact database JSON text and exact `updated_at` text, in `ORDER BY id COLLATE "C" FOR UPDATE`. It copies those strings and calls the existing `closeConnection` on a private parsed copy immediately after that result, before another await. It stores only the closed postimage and serialized terminal outbox rows. `data.id` must equal the selected physical ID, preventing malformed JSON from redirecting a write to an unplanned row. A second actual xid sample must match before a handle is issued. Preparation writes no connection, capability or outbox row.

Persistence permanently removes the handle's WeakMap entry synchronously on its first attempt. Wrong client identity, a replaced query method, another transaction, forged handles, success, failure and concurrent/subsequent reuse cannot reuse that scope. A recognized wrong-client attempt retires the genuine handle before issuing SQL; forged objects have no associated scope to retire. The actual xid is a validated PostgreSQL unsigned transaction ID string, never a supplied label. Autocommit or pool-query facades cannot produce a stable preparation xid. The same client reused after COMMIT or ROLLBACK has another xid and refuses before positive writes.

Persistence first verifies its actual xid, then rereads the complete same selector without any locking SELECT. The entire selected set and each physical/ownership/enrollment/JSON/timestamp source image must exactly match preparation. Newly matching rows, disappeared rows and same-transaction edits refuse before mutation. A fresh xid check follows that read. Each connection UPDATE additionally uses a source-exact CAS over physical ID, owner/key/credential/enrollment, JSONB source, exact PostgreSQL timestamp and actual xid, and requires exactly its planned returned ID. This catches divergence after the set revalidation without acquiring another `SELECT FOR UPDATE`. Only planned connections can be written. Capability deletion, cleanup ID/due/payload/expiry, ON CONFLICT idempotency and ordering retain the original helper's behavior. A final actual xid check precedes returning the sorted cleanup IDs.

As before, closing an already closed connection can mint another connection epoch, reason and closedAt; already ended consumers do not increment again or produce another cleanup identity. `closeConnection` and `endConsumer` are unchanged. Existing terminal material and vault epoch survive until the unchanged actual cleanup consumer clears them. Cleanup outbox rows retain the new connection epoch from their original close. The helper does not cancel or rewrite unrelated old outbox rows.

The compatibility function keeps its exact existing signature:

```js
revokeSpotifyInTransaction(tx, selector, reason = 'ownerRevoked', now = Date.now())
```

It delegates directly to prepare then persist. Unmodified V1 callers receive the same sorted ID result and existing close/cleanup semantics. When the actual Spotify relation is absent, preparation and persistence bind the same actual transaction but perform no Spotify mutation and return `[]`; no missing-table exception is swallowed. No V2 relation is queried. `flushSpotifyCleanup` is byte-identical to the pinned source, including its Date.now function default, published receipts, delay calculation and enqueue failure behavior.

Refusals are `LibraryError('spotify_revocation_invalid',409)`. SQL/serialization/other unexpected failures are reduced to `LibraryError('spotify_revocation_unavailable',503)` without retaining the original error/cause, SQL, row fields or secrets. These are internal bounded errors, not a new HTTP DTO contract. Failure does not roll back on the caller's behalf: the existing transaction wrapper owns rollback.
