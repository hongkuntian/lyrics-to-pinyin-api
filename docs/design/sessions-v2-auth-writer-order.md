## Order and API

One internal `lockAuthWriter(tx, {userIDs, credentialDigests=[], keyIDs=[], allTokens=false, allKeys=false, sessions=false})` lives in the already shared song-library store. It takes real row locks on the caller's transaction and returns only the selected raw key rows. It is neither an authenticator nor a receipt permit. Existing methods retain their signatures and perform their own credential, key, policy and crypto checks. There is no V2 import on a live path.

```text
existing library_settings anchor, when needed
  -> existing membership_settings + account nonce/identity anchors, when needed
  -> all required library_users, sorted UTF-8 bytes, FOR NO KEY UPDATE
  -> required library_tokens, sorted digest bytes, FOR UPDATE
  -> all required app_attest_keys, sorted UTF-8 bytes, FOR UPDATE
  -> affected app_auth_sessions, sorted digest bytes, FOR UPDATE
  -> Spotify connections, ORDER BY id COLLATE "C", FOR UPDATE
  -> existing capabilities / outbox / V1 deletion work
```

Unused categories are omitted. Nonlocking discovery/policy reads are not anchors. A writer never appends another existing user after token/key locks; an exact token/key now owned outside the predeclared user set refuses with the existing `app_access_revoked` error and rolls back. Key enumeration occurs under owner-user locks. All cooperating registration, rotation and key-move writers use those anchors, including absent-key registration. No lock is claimed on a nonexistent key: the owner anchor protects an owner's registration/revocation enumeration, and the existing unique key constraint arbitrates cross-owner absent-key collisions. A cross-owner losing insert still cannot move an existing key.

Current-auth uses `FOR UPDATE` on users; this writer checkpoint deliberately uses `FOR NO KEY UPDATE` in the **same user category and byte order**. Both modes conflict with each other and with every cooperating writer's user lock. The weaker user mode permits `FOR KEY SHARE` from unchanged V1 child FKs. IDs are immutable and no writer here deletes a user. This is necessary: `ListeningStore.command` holds a V1 room, then inserts `listening_commands.actor_id -> library_users.id`; deletion holds the user then scrubs that room. Making deletion take user `FOR UPDATE` would introduce a new user/room/FK cycle. Its ordinary disabled/access-field UPDATE also retains NO KEY UPDATE strength. The manual PostgreSQL test exercises the actual V1 method, not a synthetic replacement.

The only callers of `revokeSpotifyInTransaction` at the pin are signIn, signOut, delete, disableUser and revokeKey; all are changed together. The helper no longer discovers/acquires earlier auth locks from below session locks. Its existing closeConnection, credential-selector behavior, capability deletion, terminal outbox and postcommit flush remain. A future caller must provide the same complete prelocked scope, before any connection lock. Generic Spotify mutation callbacks must not call an auth-locking writer while holding a connection.

Fresh random target-user/identity and new credential/session rows are transaction-private insertions. Their unique collisions still fail; existing rows are never treated as fresh. The new Apple identity is serialized by the existing membership-settings anchor; its user FK references its transaction's own new user. Key reassignment's target-user FK, challenge INSERT's user/token FKs and session INSERT's token/key FKs were inspected explicitly. The source/target **existing** user union is never locked target-first. No global mutex, retry, timeout increase or new global serialization anchor is introduced.

## Fresh issuance and bounded expiry cleanup

AppAuth's initial and final credential checks use PostgreSQL `clock_timestamp()`, including after synchronous crypto and writes; challenge consumption uses wall time too. A late failure rolls back the consumed challenge, counter and replacement session together. Session and challenge deadlines originate at actual insertion time. Existing nullable token expiry remains accepted; finite expiry is tested freshly rather than converted into an infinite deadline. Same-credential bearer renewal leaves the key, credential and Spotify authority intact and replaces only that key's sessions. Auth 30/minute, refresh 6/minute and eight **live pending** challenges remain; the existing durable autocommit quota debit is unchanged, including failed attempts.

Apple signIn rechecks its actual source credential/key/user tuple after external Apple verification and under locks. It retains the exact PostgreSQL text deadline, including null and sub-millisecond precision. After its intentional key move and credential revocation, a fresh final DB-clock check applies that captured deadline; it does not incorrectly demand that the old tuple remain live. Target identity/reactivation and all source changes roll back if the source expired before that check. This does **not** recover exact bearer/session evidence discarded by the current HTTP/store seam. Guest creation uses DB insertion time + exactly 90 days, ACK preserves the stored deadline, and Apple issuance retains 365 days. An application cannot guarantee a deadline will not cross during COMMIT itself; return immediately from the final check with no additional application work or IO.

AppAuth challenge runs expiry maintenance before its authorization transaction, after its existing quota debit. Each of the two relations gets one separate transaction:

1. Materialize one fresh DB clock; choose at most 100 expired candidates in expiry/digest order using the existing expiry index access path.
2. Lock only that selected set in digest `COLLATE "C"` order with `FOR UPDATE SKIP LOCKED`, rechecking expiry.
3. Delete only locked candidates. No user/token/key row or FK parent is acquired by child deletion.

There is no cross-user cleanup under an actor authorization anchor, no waiting for another row owner, no loop to exhaust a backlog, and no swallowed cleanup error. A failure rolls back that relation's batch and surfaces before challenge issuance; an earlier separate batch may already have committed. A held candidate can survive for a later request. Expired rows never consume the live quota even if retained. This remains request-driven maintenance, not a new scheduler or guaranteed cleanup SLA. The 100-row bound is a candidate/lock/delete bound, not a measured IO/latency claim: Root must inspect the actual PostgreSQL plan and populated-history behavior; no DDL/index change is included.

## R2 source repair: conflict-time credential ownership

R1-01 (P2) identified an absent-digest race in `SongLibraryStore.createUser(id,token)`: distinct existing users can both read no target and lock no actual target row. Their separate user anchors do not serialize the digest's unique INSERT. R2 retains the complete coordinated R1 candidate and overlays exactly this store, its existing integration test, the manual PostgreSQL test and this document. The other nine R1 postimages are byte-identical. All preceding R1 bytes in both test files and this document are retained; this addendum also qualifies earlier scan/nonblocking wording.

`createUser` retains its validation, arguments, successful `undefined` return and transaction boundary. Its actual INSERT now uses:

```sql
INSERT INTO library_tokens(digest,user_id) VALUES($1,$2)
ON CONFLICT(digest) DO UPDATE SET revoked=false
WHERE library_tokens.user_id=EXCLUDED.user_id RETURNING digest
```

No returned row throws `LibraryError('token_collision')` (409) inside the same transaction. The foreign row is not updated: owner, revocation, finite/nullable expiry, creation metadata and associated data remain unchanged. All losing-owner credential revocations and any fresh losing user roll back. A foreign row found by the initial discovery keeps the same error; a foreign row discovered by this method's token-only helper scope after that read maps the helper's `app_access_revoked` to the same `token_collision`. Only that known `LibraryError` is mapped, at this call site; other helper callers and database errors keep their policies. No foreign owner anchor, retry, timeout, mutex, owner reassignment or extra query is added. PostgreSQL may lock the conflict tuple while evaluating the predicate; this is not an assertion that absent-row prelocking protects it or that the operation never waits.

Same-owner reuse still un-revokes its own digest and revokes its other credentials without extending expiry or resetting owner, creation time, flags, access kind, usage or saved data. This is existing V1 behavior, not a V2 no-resurrection implementation.
