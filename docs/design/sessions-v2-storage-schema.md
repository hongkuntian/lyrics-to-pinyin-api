## Physical choices

Exactly eight tables live in the private `listening_v2` schema. Domains and four small protection triggers are supporting schema objects, not a new identity system. Existing library users/tokens, App Attest keys, account identities and Spotify connections remain the identity/credential authorities.

| Relation | Purpose and principal access paths |
| --- | --- |
| `output_guards` | Independent non-PII safety ledger; scope uniqueness, provider-account lane, original-install lookup, bootstrap lookup. No expiry or cascading dependency. |
| `privacy_personas` | Immutable original persona and canonical controller/generation; indexed controller, exact credential dependency, actual credential deadline, original key and bounded scrub cursor. |
| `rooms` | Immutable protocol 2, host install scope, bounded JSON plus scalar revisions/quotas; active-host/code uniqueness, expiry, host privacy, persona-reference GIN and retention indexes. |
| `returning_grants` | Host-install/pair uniqueness, revocation/generation, privacy-controlled sides and approver provenance; indexed host pagination and every persona side. |
| `command_receipts` | Redacted durable acceptance/refusal and replay keys; creation uniqueness independent of room, room-command uniqueness, actor scrub, room and retention selection. |
| `semantic_events` | One physical relation for separate semantic, reaction and End lanes; unique global and lane sequence, semantic-first cursor reads, actor scrub and retention selection. |
| `outbox` | Coalesced wake/execution/expiry/privacy/asset work; unique job key, typed FK references, indexed due/claim/retention and room/guard/persona/asset selection. |
| `private_profile_assets` | Sanitized private object references; current/staged install uniqueness, persona/generation lookup and staged/deletion/backup deadlines. No bytes or public URLs. |

Every primary key, unique constraint, index and FK includes environment. Valid environment values are `production`, `development`, `test`, or `preview:<deployment-identity>` with 1–120 ASCII letters/digits/dot/underscore/hyphen after the colon. Generic `preview` is refused. A preview hostname/deployment ID must be normalized by trusted configuration into that identity, never selected from a request. Development/test are for their deliberately shared local scopes. Missing identity fails before storage. Jobs include the same environment and numeric `version:2` in bounded payloads; relational references always pair that environment with their ID.

All V2 FKs use `ON DELETE RESTRICT`. There are deliberately no V2 FKs to the existing globally keyed user/key/token/connection tables: those cannot express the V2 environment composite and their lifecycle must not cascade safety away. Same-transaction hooks must lock and validate those authoritative rows, not infer liveness from their stored identifiers. `approved_session_id` in a returning grant is an environment-scoped audit reference, intentionally not a retention dependency on a room. Safety capsule references likewise do not require the original room to survive.

`originalPersonaID` is the immutable `persona_id` plus its immutable original principal/key. A live-origin partial unique index permits one live incarnation of that tuple per environment. After permanent withdrawal, a new explicitly consented incarnation may use a new UUID; it cannot reuse the old persona's rights, assets or references. An expired row still marked live must first undergo the bounded withdrawal CAS. Re-enrollment must never reset or reactivate the old row. There is no alternate credential-family or account-history authority.

## What SQL enforces

Revisions, epochs, send ordinals, clock milliseconds, privacy/asset generations and claim epochs use nonnegative bigint values bounded by JavaScript's exact-integer ceiling, `9007199254740991`. They are returned/parsed according to the future typed store's integer policy; a `pg` bigint string is not permission to coerce an out-of-range number. SQL rejects negative/out-of-range writes. The four triggers preserve guard scope/fences, persona origin/withdrawal/controller restrictions, room identity/lifetime/monotone revisions and lifetime counts, and asset identity/withdrawal. They are invoker functions with fixed `pg_catalog` search paths and no public execute grants.

Room `state` must be an object with occurrence/visit arrays. Their lengths equal scalar lifetime counts, bounded at 100 and 512. The sum of observed visits and traversal/inverse/desired/other accepted credits cannot exceed 512. Semantic committed+reserved slots cannot exceed 20,000; reactions cannot exceed 10,000; receipts committed+reserved cannot exceed 30,000; executions committed+reserved cannot exceed 1,000. End retains an independent reserved flag and 8,192 bytes. These are row-local bounds; the migration does **not** automatically update counters when another relation changes. End/cleanup reservations are not released by a room status change.

The room protocol is always 2, its expiry cannot exceed creation+8 hours, and neither protocol, original host scope, provider nor lifetime can change. End cannot reopen the room. Ended room retention fields require at least End+24 hours for raw events and End+30 days for receipts. There is no automatic expiry, scheduler, deletion or playback behavior in this migration.

Guards default to `uninitialized`/`blocked`. A missing guard has no initialized meaning. An initialized row requires a positive bootstrap epoch/minimum writer generation and a qualification-manifest hash. Uninitialized/legacy-quarantined rows cannot be idle/reserved/executing; they may preserve an existing uncertain send while bootstrap evidence is invalidated. A sent marker needs an execution ID, positive send ordinal, endpoint/body hash, claim identity and executing/uncertain lane. One partial unique index permits at most one reserved/executing/uncertain lane per environment/provider/account binding across lineages/output scopes. This is stronger than per-device concurrency; actual scope intersection is still a store responsibility.

The guard keeps bootstrap/fence/revision/claim/send identity, observed/credit/event/receipt/capsule reservations, retained bounded safety evidence, and dedicated terminal reservation space. No user, persona, room or credential FK points out of it. Deleting a room, persona or credential cannot remove it. Guard `DELETE` is refused by trigger even for ordinary owner-issued deletion; neither application role receives DELETE or TRUNCATE. This foundation intentionally supports retaining/compacting a resolved tombstone, not removing guards. Privileged schema owners can change DDL, so operational separation is still required.

Persona SQL requires a guest's exact credential digest and finite deadline no later than persona creation+90 days, the original guest principal/key as controller, and a <=512-byte compact logical record. The deadline must be copied from the actual authenticated credential, never replaced by a rolling 90-day default. Guest dependency and deadline cannot be replaced/extended in place. Controller/status changes require a newer privacy generation; withdrawn data cannot return to live. Narrow live guest-to-Apple transfer is structurally possible; changing an Apple controller to another account/guest is refused. Authorization and the actual live-before-deadline transfer test remain in the future hook.

Creation/restart receipts have unique `(environment, principal_binding, key_binding, command_id)` across both actions and all session IDs. Other command keys are `(environment, session_id, principal_binding, key_binding, command_id)`, independent of action. A duplicate insert therefore conflicts; SQL alone does not return the original receipt or distinguish equal-body retry from different-body conflict. The store must compare the immutable canonical hash under its locks. `room_id` equals `session_id` when present; creation/restart refusal and standalone privacy erase can retain a receipt without a room. A creation receipt requires the fixed ticket-expiry binding, and retention cannot precede either the ticket deadline or creation+30 days. The future store reserves retention through the room's maximum expiry+30 days before insertion, then rechecks against actual End.

Receipt principal/key bindings are stable, environment-scoped, server HMACs of the **exact authenticated** existing principal/key IDs, with an explicit key version. They preserve minimal replay denial after privacy erasure without retaining raw identity as the replay key. Actor persona/generation and redacted result can be scrubbed independently. The store must preserve binding continuity across key-version rotation, look up retained versions, and compare canonical bodies; rotating a key cannot create a fresh replay namespace. No arbitrary caller digest is accepted. These bindings are not recording matches: exact provider recording/item IDs must remain in the approved typed room/capsule records without hash/metadata substitution.

Event lane sequence uniqueness and maxima bound simultaneously retained rows to 20,000 semantic +10,000 reaction +one End per room. Global `seq` is 1–30,001; each lane has its own cursor. Actor references carry a privacy generation. Events and receipts reject oversized JSON, but have no consent/ACL evaluator. Retention timestamps are indexed admission fields, not proof that a deletion worker honored them or that a lifetime slot cannot be reused after deletion.

Outbox jobs have typed environment-scoped room/guard/persona/asset FKs and kind-specific required references. Room execution jobs carry guard revision and send ordinal. The separate `guard_cleanup` kind requires only an existing environment-scoped guard plus its revision/ordinal, with room/persona/asset references absent; durable cleanup therefore remains representable after room deletion. Account-role insert columns still exclude guard/revision/ordinal, so only the runtime role can enqueue this work. This representation neither grants execution nor bypasses Release, current captured ownership, reserved capacity or pre-send CAS. Payloads bind environment/version. Attempts are 0–10; due/retry fields fit within creation+24 hours; a claimed row needs nonce, positive epoch/attempt and bounded deadline; terminal rows retain completion and at least completion+24-hour deletion fields. Future enqueue/claim code must check current generations, use claim CAS and never treat lease expiry as Release. These checks do not prove an external queue subscription or downstream consumer is fenced.

Assets allow one current and one staged object per install/environment. Sanitized objects are at most 256 KiB and 256×256, in the JPEG/PNG/WebP allowlist. Stage lifetime is at most one hour. Revocation requires object deletion due within 24 hours and backup deletion due within 30 days of withdrawal. Deleted objects have no object key. An asset's origin/content identity is immutable; revoked/deleted rows cannot return to current/staged. Generation bounds and persona FKs do not authorize image reads or uploads.

## Logical size policy and physical overhead

Limits use `octet_length(jsonb::text)`, PostgreSQL's normalized JSON text with spaces and UTF-8 escaping, rather than JavaScript UTF-16 length, toast size or compressed heap size. The future encoder must budget this conservative normalized representation before admitting work. A compact no-space JSON byte count can be smaller; it cannot bypass the SQL bound. Oversized exact IDs/metadata refuse, never truncate or substitute a nearby recording. The store must measure its real encoder against this policy; it cannot claim the design's example encoder has already passed.

| Object | SQL encoded policy |
| --- | --- |
| Room JSON | <=262,144 bytes, independent of scalar columns/arrays and dependent tables |
| Guard safety capsule | <=131,072 bytes, object shape; scalar reservations are separately bounded |
| Persona | <=512 bytes for the explicit compact array of **all** columns, including environment and cursor |
| Returning grant | <=1,024 bytes for its explicit compact column array |
| Receipt | Result <=512 bytes; aggregate compact column array including result <=1,024 bytes |
| Event | Payload <=512 bytes; envelope, SQL row and indexes are additional |
| Outbox | Payload <=4,096 bytes; identifiers <=160 bytes, fixed typed metadata additional |
| Asset | Image bytes <=262,144 outside PostgreSQL; only bounded typed metadata/random object key in the table |

The architecture's disjoint room slices still require the typed encoder: 102,400 occurrence bytes, 98,304 observed+credit bytes, 16,384 member/admission/profile-reference bytes, 32,768 executor/plan bytes, 4,096 fixed bytes and 8,192 terminal bytes. SQL checks the whole room and array counts; it does **not** validate each occurrence <=1,024 bytes, each compact visit <=192 bytes, each sub-slice maximum, six reaction counters, exact observed ancestry, immutable occurrence metadata, append-only visit contents or per-element safe integers. The focused boundary test intentionally uses null array stand-ins to prove only the count/escrow constraints. Such a row is not a valid typed Sessions room.

Similarly, guard JSON is not yet a complete typed safety capsule. Its <=100 exact mappings×512 bytes, <=8 substeps×4,096 evidence bytes, <=32,768 plan/scalar bytes and <=14,336 fixed/framing bytes require typed validation and actual encoder measurement. Persona admission must also reserve its worst-case withdrawal timestamps and bounded cleanup cursor within the 512-byte record before retaining PII; the aggregate SQL check alone does not pre-reserve that expansion. Reject an overlong identity/environment/cursor before admission; never truncate identity or defer mandatory withdrawal because the current live record filled the bound. The future admission transaction must reserve the **combined** eventual capsule/terminal expansion within 128 KiB, not add the independently bounded reservation scalar on top of a full capsule. No PII, name, image, full display metadata or decrypted OAuth may enter it. SQL's generic JSON bound cannot prove that whitelist.

All bounds describe logical encoded content. SQL headers, null bitmaps, alignment, scalar mirrors, persona-reference arrays, TOAST, indexes/GIN postings, WAL, backups, replicas and retained receipt/event rows add storage. No physical heap/index cost, throughput or affordability claim follows from the payload caps.

## Privacy authorization and bounded cleanup still required

There is one canonical current controller/generation per persona. Every privacy-bearing domain reference must carry its original persona ID and authorizing generation, including nested room membership, contribution/recap/share/consent state, receipt actors, event actors and assets. Relational actor/side fields exist here; the room's `privacy_persona_ids` is an indexed **selection mirror**, not an authorization source. The typed transaction must maintain that mirror for every referenced member/admission/persona and ensure it exactly covers the nested state. Its cap is 25 lifetime members +300 lifetime requests +10 pending slots; duplicates do not expand domain budgets. Nested references have no independent FK or authorization merely because they are in JSON.

The future `GuestLive` read/commit predicate must join the actual enabled user, unrevoked key still owned by that guest, bound credential owned by the same guest/unrevoked/unexpired at current DB time, and environment/audience/bundle. Stored expiry alone is insufficient. Every audience checks this predicate at read/commit, including private recaps, prejoin/share projections, images, receipt/event reads, grants and upload callbacks. Use `clock_timestamp()` or equivalent actual authorization time after locks, not transaction-start `now()` across a deadline. There is no auth hook/read predicate in this migration and no claim that retained PII is automatically denied or scrubbed yet.

Required hook entries remain signIn, signOut, delete, admin user/key revocation and library credential rotation/digest reuse. Transfer only live G/K to verified A before shared C closure; other C-dependent personas withdraw, never transfer to A. A→B keeps A-controlled history with A. Delete A selects canonical controllers including former G/K and excludes unrelated personas. Token deletion/unrevocation/expiry extension or key/user reenablement cannot resurrect withdrawn generations. Ordinary 15-minute bearer renewal with the same live credential changes none of these privacy rights.

Indexes support <=100 dependency/persona selections, and a durable cleanup outbox cursor per persona. An expiry sweep runs once per minute, bounded to 100 indexed rows, with one claimed batch/cursor; revocation hints coalesce. Each transaction rewrites at most one <=256 KiB room or 100 other bounded rows, then yields. For room selection use **both** `ARRAY[environment::text] @> ARRAY[$environment::text]` and `privacy_persona_ids @> ARRAY[$persona::uuid]`; the built-in two-column array GIN supports those predicates without installing `btree_gin`. Queries using only `environment=$1 AND persona=ANY(array)` do not establish this GIN path. Other cleanup uses `(environment, actor_persona_id, session_id, cursor)` or asset/controller indexes. Use keyset cursors and stop on the batch bound, not full history enumeration. Receipt cursors include the complete principal/key/command suffix, since the same command UUID may legally exist under distinct principal/key bindings. GIN posting-list work and physical selection cost still require load measurement; LIMIT bounds returned/rewritten objects, not index IO by itself.

Neither the scheduler nor this query implementation is included. Immediate logical withdrawal at credential invalidation/expiry must hold even while physical cleanup is delayed. Deletion deadlines, backlog/oldest-due alarms and admission suspension when cleanup falls behind require real object-store/scheduler qualification. Guest setup must disclose that guest profile/recap access expires with the underlying access (up to 90 days); sign-in while live preserves only that installation's history. Old identifiers/deadlines never authorize a privacy recovery shortcut. Erasing a persona must preserve exact recordings/order/counts anonymously and keep non-PII guards indefinitely when Release is unsupported.

## Roles and transaction boundary

Conditional grants target the existing **separate** `lyra_runtime_v1` and `lyra_account_v1` roles. If a role is absent, migration does not invent a login or credential. Root must verify actual role presence/grants before enablement. PUBLIC has no schema/table/function privileges here. Application roles get USAGE, no schema CREATE, table ownership, DDL, TRUNCATE or guard DELETE. Existing public schema/V1 privileges are untouched.

Runtime can create/mutate the domain tables and compact non-guard data; persona controller-transfer columns are reserved to the account role. Account gets read access and column-level fencing/controller/redaction/revocation grants, not room creation, receipt identity/hash rewrite, guard bootstrap/manifest/capsule/send mutation, or persona/guard deletion. Its limited outbox INSERT permits privacy/asset cleanup references; other kinds require room/guard columns it cannot insert. Runtime processes cleanup state transitions. No account role privilege permits transfer of active audio authority.

These are trusted backend service roles, not user-facing SQL roles or row-level user auth. They do not enforce public membership/consent or provide a safe generic SQL endpoint. Account fencing/redaction column grants enable the planned hook to operate in the **existing account transaction**. They do not implement it. Both account and runtime pools must address the same authoritative PostgreSQL database/schema; pass the existing transaction `db` into the hook. Separate URLs/pools, DDL grants and a PGlite role test do not prove that production configuration. Missing needed hook permissions/configuration keeps V2 disabled; never use a second pool/after-commit scrub to imitate atomicity.

The approved lock order remains: existing settings/identity serialization anchors first; sorted users/tokens; sorted App Attest keys (including host grant anchor); sorted Spotify connections; sorted output guards; sorted personas; host grant scopes; rooms; deterministic receipt/event/outbox rows. Acquire scopes up front. Discovering an additional earlier scope aborts/restarts the bounded transaction. No provider/catalog/image IO under locks. The migration has no stored reducer that obtains this order.

A future command transaction must dedupe, reauthorize current credential/controller/generation/membership/deadline, compare revisions/body, reserve all terminal/visit/event/receipt/byte allowances, mutate the room, allocate contiguous cursors and insert receipt/events/coalesced outbox atomically. Create/restart room+receipt/permutation atomicity, different-payload conflict outcomes, reservation/counter correspondence across relations and all competing transaction orderings are **unimplemented** here. DDL constraints and a rollback test cannot qualify that later transaction code.

## Safety, retention and rollout gates

Use the same Release predicate for ordinary successor writes, cleanup, reservation retirement and owner handoff: no remaining possible writers AND either proven never-dispatched or qualified terminal/neutralization evidence for the exact ordinal/scope. A manifest/evidence hash is a bounded pointer, not evidence by itself. Store code must load/check retained immutable evidence; no operator assertion, fresh snapshots, timeout, claim deadline, End, new token/room or elapsed time can release uncertainty.

Before first acquisition, require the qualified minimum writer fence across V1/V2, solo/recap, native actors, cleanup and queue consumers plus complete predecessor terminal coverage or genuine unused/disjoint scope proof. Unknown legacy reach uses an account-wide marker. A missing row remains uninitialized. Initialization/revision CAS, intersecting-scope checks, stable verified account/lineage continuity across reconnect and HMAC versions, <=4 retained scopes/install and <=16/account are **future indexed/locked store invariants**, not claims enforced by these eight tables. Guard count exhaustion refuses new scopes rather than evicting evidence. The unique account lane cannot prove scope disjointness or external terminality.

Private recaps persist until explicit deletion. Raw events retain through End+24 hours, receipts through End+30 days and expired-ticket replay remains refused. SQL timestamps/indexes require a later retention worker; that worker must not reuse lifetime cursors/counters after deletion or remove replay results before their reserved deadline. Terminal requests' PII, logs, staged/private images and backups follow the architecture's distinct deadlines. Guard safety evidence survives **all** those deletions; no TTL release, down migration or incompatible pre-gate rollback is supported. Ended-but-uncertain observations may still update retained non-PII safety truth without recreating an erased private recap.

The runner is intentionally unchanged, so migration 030 is not automatically applied. Root reviews/registers the immutable migration, applies additive DDL with capabilities off, verifies both roles/pools and hooks, then qualifies shared writer gating/bootstrap/Release, privacy/deadline behavior and packaging/edge/provider/native capabilities independently. Rollback retains schema, guards, writer fence, compatible readers, withdrawal and scrub. No enabled route/capability, live migration, account/provider request or infrastructure change belongs to this slice.
