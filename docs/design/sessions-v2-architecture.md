## Version boundary and request protocol

Keep `/api/sessions` version 1 validator, DTOs, actions and routing strict/compatible; V1 fixtures on a proved independent scope keep their behavior. The shared pre-send ownership gate and legacy-scope initialization below are the explicit execution-policy additions required to stop old/V1 cleanup or solo routes bypassing quarantine; they do not reinterpret V1 as V2. Guard absence is not an independence or clean-state proof. Add separately routed `/api/sessions-v2` and its explicit `.js` alias through the existing provider gateway, keeping the 12-function packaging ceiling; the edge/routing section below defines the exact boundary. Capability discovery is authenticated and returns `{version:2, schemaRevision:1, capabilities:[...], limits:{...}, reactionSet:{revision,ids:[six IDs]}}`. V1 never receives V2 room IDs, membership or instructions. A room has immutable protocolVersion; never migrate an active V1 room or mix protocols. Old app invite fallback remains a generic landing page/update explanation. Unsupported capability returns explicit refusal; never silently disable Ask or reinterpret V2 join as V1 join.

All JSON schemas reject unknown keys, wrong types, unsafe integers, invalid UUIDs and oversized values. Mutations:

```json
{"version":2,"action":"queue.add","sessionID":"uuid","commandID":"uuid","expected":{"queueRevision":12},"payload":{"catalogSelectionID":"opaque","placement":"end"}}
```

Bearer app-auth credential authorizes principal/key; neither actor ID nor host role is caller supplied. `commandID` required for every mutation including create/join/cancel/reaction/acks. `expected` admits only action-relevant revision fields. Reads do not increment versions. Response `{version, serverTimeMS, command:{id,status,result,error?}, snapshot?, events?, nextCursor?}`. A success means durable acceptance, never audio execution. Command statuses: accepted, executing, applied, refused, expired, uncertain, cancelled. Errors: invalid_request(400), unauthorized(401), forbidden(403), not_found(404, hides membership/invitation existence), conflict(409 with permitted current revision), expired(410), rate_limited(429 Retry-After), unavailable(503). No private state in errors to nonmembers.

Create/restart require an authenticated server-issued creation ticket before submitting intent. Ticket MAC binds version, environment, principal ID, App Attest key ID, action, server-allocated room UUID, command UUID, canonical body hash, source recap revision for restart, random nonce, server issuedAt and notAfter (10 minutes). Ticket issuance never creates a room. Server refuses caller-selected expiry, future-issued or expired tickets before opening a create transaction; retries retain the same ticket. Issuance after expiry is a new explicit intent with new command/room UUID, never automatic renewal of an old request. The server cannot reissue a ticket for an old client UUID: room UUID is server allocated in ticket issuance and includes authenticated issuance time; issuance accepts no supplied room UUID. Command UUID is likewise server allocated for these two actions. This differs deliberately from client-generated IDs on room mutations.

Within ticket validity, unique `(env,principal,key,commandID)` receipt plus unique room ID enforces one create/restart; duplicate with different hash conflicts. Receipt and room commit atomically. Authenticate current entitlement before returning any saved result. Keep creation receipts at least until ticket expiry and then through end+30 days. After receipt deletion an old ticket is cryptographically expired and returns `expired`, never re-creates a room; forged expiry fails MAC. Signing-key retirement rejects unknown old key IDs, never falls back to unsigned acceptance. A lost result after ticket expiry requires authenticated room lookup, not resubmission with a fresh ID. Room mutations dedupe `(env,sessionID,principal,key,commandID)` with canonical hash including protocol, payload and expected fields; exact retry returns original redacted receipt, altered retry conflicts. Closed/missing/expired room refuses all new mutations even after its receipts are deleted. Persist pending IDs/tickets before send; resolve network ambiguity by lookup. Valid refusals are durable within bounded receipt storage; pre-transaction failures retry the same intent. No permanent replay table or new identity system is required.
## Authoritative state, storage and atomicity

Use PostgreSQL as authority and retain the existing row-locked room/transactional outbox foundations. V2 records are separately namespaced; V1 consumer never sees them. Do not mandate fifteen normalized tables. Initial physical design uses eight V2 relations: independent output guards and privacy-persona control records, plus rooms (bounded JSON domain state), host-scoped returning grants, command receipts, semantic events, outbox, and private profile assets. Room JSON holds members/admissions, 100 immutable occurrence metadata records, at most 512 compact actual observed visit records with reaction counters, with fungible credits reserving all possible future observations, one active control plus bounded control summaries, share generation and executor state. Grants are independent because they cross sessions; events/receipts/outbox are independent because they need indexed retention/claims. Auth keys, library users/tokens and Spotify connections reuse existing relations. The two new small indexed relations are necessary because quarantine and privacy control outlive a room, key move and room deletion; neither is a social identity or credential-family service. Split another room substructure only if measured contention/size requires it; constraints and row locks must enforce the same semantics.

Every key/index and job payload includes environment (preview deployment identity, not generic `preview`). Runtime gets least-privilege grants; no raw public SQL. A room contains sessionRevision, queueRevision, settingsRevision, transitionRevision, stateVersion, eventSeq, authorityEpoch, observationSequence, current occurrenceID/visitID, desired/applied queue revisions and executor kind/context. `transitionRevision` advances only for semantic playback transitions: confirmed start/adoption/advance/restart, accepted non-noop transport or future-path edit, applied effect/inverse, detach, End or authority change. Future-path edits invalidate an unaccepted Undo because its restored path is immutable; progress and unrelated settings do not. Ordinary same-visit position/playing confirmations advance only observationSequence and replace the progress snapshot. Playing-state changes not attributable to an already accepted control are semantic and invalidate Undo. No progress event/outbox/command receipt per routine observation; use last sequence/hash for duplicate ACK.

Authority stores original `(principal,keyID,bundleID,audience,attestEnvironment)`, current valid credential binding and provider authorization/context epoch. Worker execution lease stores claimant nonce, claim epoch and deadline separately. Bounded snapshots exclude image bytes and raw receipts; <=256 KiB encoded room JSON, checked before accepting additions. End always has reserved fixed space. Control history/events contain references and bounded pre/postimages, not whole snapshots.
Recording = `{provider,catalogID,storefront,versionMetadata:{title,artist,album,durationMS},catalogRevision}`; provider ID is exact recording authority, metadata is immutable snapshot not matching authority. Selection tickets bind this tuple/session/provider/storefront with five-minute expiry; revalidate availability outside lock then verify binding inside. No title search replacement, cross-provider substitution or duration-only matching. Duplicate recording IDs remain separate occurrence UUIDs. A replay visit of an existing occurrence is a new visitID; history and counts bind visit, preserving distinct repeat plays. Explicit history replay always creates a new occurrence; start/adopt also allocate an occurrence if there is no existing session occurrence for that exact source item. No history credit on queue acceptance, intent or inference alone.

**One lock order.** Identity mutations first take existing `membership_settings` row 1 and the applicable `account_identities` row (as AccountStore already does); existing admin/library-setting serialization anchors, when needed, are acquired before these in a fixed documented order. Other paths never acquire such anchors after a lower lock. Then required library-user/token rows in sorted ID/digest order, all required App Attest key rows in sorted key order, existing Spotify connection rows in sorted ID order, output-guard rows in sorted scope order, privacy-persona rows in sorted ID order, host grant scopes, rooms, and receipt/event/outbox rows in deterministic ID order. Acquire required keys up front, including a host-key grant anchor; never discover and lock a smaller key from inside a room lock. A missing/discovered additional scope aborts and restarts the bounded transaction rather than inverting order. Reads touching privacy take compatible shared locks on current credential/key/controller generation; ordinary room-only paths skip irrelevant rows. Check credential expiry using current DB time at the authorization/commit point, not transaction-start `now()` for a transaction spanning the deadline. No provider/image/catalog IO inside locks. The V2 hooks must preserve the existing key-before-connection order in `revokeSpotifyInTransaction`; identity hook entry is before that revocation scan. Registration/session issuance and credential rotation must share the user/token anchors so a newly registered key cannot escape withdrawal. Deletion, sign-in, approval/Forget, asset/receipt reads and execution pre-send all follow the same order.

Use unique constraints/CAS as well as locks. Recheck current principal/key/credential revocation, privacy generation, membership, expiry, permission, versions, output quarantine and capacity under locks, not only at HTTP authentication. In one short transaction: dedupe, authorize, validate expected revisions, mutate state, reserve capacity/terminal allowances, allocate contiguous event seq, increment relevant revisions/stateVersion, insert redacted receipt + semantic events + coalesced outbox marker, commit. Saved receipt lookup is also a currently authorized, generation-aware read. Progress/challenges update bounded snapshot state without durable event/receipt. Retry serialization/deadlock failures at most twice with the same command ID, then return retryable conflict; no hidden provider retry.

Observation transactions can advance progress snapshot/observationSequence without invalidating queue/settings edits. Queue mutations advance queueRevision; semantic transitions advance transitionRevision; settings advance settingsRevision. Snapshot and its event watermark come from one consistent DB read transaction. Event reads are ordered seq > cursor at that watermark; no older snapshot replaces newer native state. Native store is scoped to authenticated installation + session + local generation and discards replies after leave/account/session switches.

Admission races: approve vs deny/cancel/expiry first locked terminal transition wins; losers receive terminal result, no new grant. Capacity tested at admission commit, not request creation. Existing approved member request returns existing membership. Turning Ask off affects new requests only; pending request remains decidable/cancellable. Forget increments/revokes grant; concurrently admitted member remains admitted and UI says Forget affects future sessions. A later explicit approval may grant again; that is visible audit evidence. Ask=false joins do not create remembered grants because nobody approved. Trust follows the hosting installation scope, not approver's other rooms: record approver provenance without trusting this guest with every host.

## Identity, privacy, invitation and abuse model

Identity is grounded in the inspected backend `api/utils/app-auth/store.js` at `9077a2e` (blob `d81acfb29b5e7085e75b1c44b4d37e87d13ecba9`), plus `app-auth/admin.js`, `song-library/store.js` and `spotify/store.js`. `credential()` requires an enabled library user and unrevoked/unexpired library token. A 120-second challenge binds that token digest, user, key, bundle, audience and purpose. Registration matches user/bundle/audience/environment and never issues a bearer. `session()` locks the registered key, consumes the challenge, verifies a strictly increasing assertion counter, deletes prior sessions for that key, and issues a 15-minute `lyra_s_` bearer. `authenticate()` rechecks session, key, library credential and user revocation/expiry, and returns `{id,keyID,bundleID,credentialDigest}`. Thus normal bearer renewal preserves installation identity but invalidates the previous bearer; it must not end a room merely because the bearer string changes. Use existing policy audience/environment as additional server-derived binding, not caller data. A second key for the same library user is a different installation and cannot acquire host authority.

Library `createUser()` credential rotation revokes older library tokens. This invalidates associated app bearers and `spotify.store.ownerValid()` bindings; no invented credential-family continuity is available. V2 fails closed on old credential revocation, freezes new effects, and requires explicit original-key reauthorization with a new valid app session and broker connection epoch before resuming; no automatic connection rebinding. Key/account revocation ends authority and room, as distinct from ordinary bearer expiry. A host app's absent/expired 15-minute bearer does not expire valid durable broker authority: broker checks stored original key/user/library credential and provider grant before each claim/call, as V1 does. Reinstall/key loss never transfers authority. Current admin disable/revoke paths also revoke Spotify access; V2 adds transactional room fencing to those existing paths, not a new identity service.

None creates a credential family. V2 adds transactional fencing/guard retention to signOut, deletion and admin credential/key revocation too; signOut does not transfer historical privacy controllers. Select **narrow historical privacy-control transfer**, preserving nights at sign-in. A V2 privacy persona is an internal immutable `(environment, originalPrincipalID, originalKeyID)` record, not an account merge. Every privacy-bearing object or reference (profile/name/photo, consent, membership/history attribution and private recap access, contribution, returning grant side, share and command receipt actor) stores immutable `originalPersonaID` and its authorizing `privacyGeneration`; the indexed persona record is the canonical `currentPrivacyController` and current generation. No mutable duplicate controller field is an independent authority. Controller is initially guest `(G,K)` or authenticated Apple account A, server derived. Original persona never changes. All permission checks join its **current** controller/generation; an original `userID` match alone is insufficient. Historical recap/control rights do not include active room membership, admission approval, host settings, transport, OAuth or audio ownership. Immutable exact recording/order/reaction counts survive PII removal.

**Database boundary.** Pinned `membership/database.js` uses `LYRA_ACCOUNT_DATABASE_URL`, while `song-library/database.js` uses `LYRA_LIBRARY_DATABASE_URL`; separate pools/roles do not establish separate data stores or prove shared deployment configuration. Add narrowly scoped account-role hook grants and test role permissions/rollback. No second-pool commit, after-commit scrub or cross-database atomicity claim is acceptable; fail V2 enablement if this configuration/transaction boundary cannot be established. Deployed DB configuration is uninspected.

**Same-transaction V2 hook.** In the existing `AccountStore.signIn` transaction, after target Apple identity is known and before key reassignment/old-credential revocation commit, acquire the ordered user/token/key/connection/guard/persona/grant/room locks. Perform the existing Spotify revocation in its key-before-connection position, with V2 guards captured before its cleanup can dispatch after commit. If the actual source principal is guest G and that persona is still live at commit, transfer **only** the `(G,K)` historical privacy-control record and its controlled references to verified A, increment generation, remove its guest-credential dependency, and preserve private nights/access for A. An already expired/withdrawn guest persona cannot transfer or resurrect; sign-in itself must recheck its source authentication at commit. No other G key/persona moves. Revoking the shared old credential withdraws remaining dependent guest personas by the rule below in this same commit; it does not give A their privacy rights. Withdraw the moved persona's old prejoin and public-name consents across projections/shares; invalidate old upload/asset/resolve generations, clear PII-bearing cached events/receipts or make them inaccessible via generation-aware projection before commit. Keep private recap name/photo only under the disclosed private-room consent and current controller; rebind retained private references to the new generation so A can retrieve them while every old G/K asset capability denies. Fresh explicit consent is required for new room/prejoin/public use. End/fence any G/K-hosted room, cancel never-dispatched intents, leave its guest memberships and pending admissions, invalidate active capabilities and server ownership generation (client ownership actor persists/increments its local generation before initiating sign-in and discards old results), and retain all already-sent effects/credits in the output guard. No host/audio authority transfers to A.

If source is **Apple A -> Apple B**, do **not** transfer any A-controlled history, including earlier G/K history now controlled by A. A retains its account privacy rights and can use another currently authenticated A install to revoke/delete them; B gets only B's own persona and new explicit membership. K's old A memberships/host authority still end/leave and public/prejoin consents for that old K persona withdraw. Same-account A -> A does not transfer or erase history, but credential replacement still fences old active authority; explicit fresh authorization and the release predicate are required. Rollback leaves key, controller, consents, receipts and generation unchanged. These hooks are V2 additions to actual functions, not claims that existing AccountStore already supplies them; no other app data domain is migrated.

Returning pair ID remains server HMAC(secret version, environment || random host-install scope || guest **verified key K**), with no caller principal/old-persona claim. The physical-install grant may persist across same-K G->A or A->B, because P34 remembers an install, **not** an account's friends. ## Host execution, lease fencing and recovery

V2 uses a version-specific broker consumer for Spotify, preserving V1’s service tick, captured target, owned playlist/context, connection epoch and original host credential checks. Native Spotify code submits user intents and displays observations only; it never also writes the session queue/transport. Apple Music uses the original-install native adapter. Durable session authority lasts until End, eight-hour expiry, original key/account/provider revocation or explicit context detachment; it does not require host-app heartbeats for Spotify. The broker can refresh OAuth and apply admitted queue/control intents while the app is absent. Confirmation of a different owned target/context requires explicit original-host action, new authorityEpoch and reconciliation; never silently follow an arbitrary active device. Device labels/copy must reflect the confirmed target when it is not the phone.

An execution lease is a separate short mutual-exclusion claim: initially 20 seconds, renew at 5 seconds during native work; broker renews within bounded job execution. **At most one execution lane across all intersecting output-guard scopes**, including queue, transport, handoff, options and cleanup. Claim binds executionID, nonce, authorityEpoch, desired queue revision and transitionRevision. Claim expiry never permits another writer while a prior send may still apply. Apple native original key or internal host-bound Spotify broker only; no guest claimant. External IO stays outside DB locks with fenced pre-send and result transactions. Secrets never enter member DTOs.

### Durable output quarantine and the single release predicate

Create a small independent durable output guard at `(environment, provider, providerAccountBinding, connectionLineage, capturedOutputScope)`. Spotify uses a server-verified provider subject/account binding when obtainable and captured device + owned context/playlist; connection UUID/epoch is provenance **within**, not a replacement for, the lineage. If verified account continuity cannot be established on reconnect, retain the old guard and refuse potentially overlapping authority. A new token, connection row, principal, key or room must not manufacture a fresh lineage. Account-level endpoints reserve an account-wide wildcard; transport/device changes and options also intersect every captured-output guard the endpoint might affect. Apple uses the original installation's native ownership actor and captured player/output route with persistent generation and a server guard for session handoff; uncertain process-death state is not erased by relaunch. If scope independence is unproved, treat scopes as intersecting. In addition to scope intersection, one executing/uncertain lane per verified provider account serializes device scopes; device changes cannot bypass an uncertain same-account operation. The guard persists across End, room/recap deletion, local solo/recap ownership changes, sign-in/out, credential revocation/reconnect and new rooms. This is a safety ledger, with pseudonymous scope/effect IDs and reservations, no member PII or live OAuth token.

Each possible external mutation has one durable send ordinal, endpoint/body hash, captured scope, old finite applied path, candidate finite path, generation/claim identity and reserved credits/events/bytes. Before handing the request to IO, commit a `may_have_been_sent` marker while holding guard/room locks; any crash after this marker is conservatively already-sent. No second dispatch until that ordinal satisfies **Release(e)**:

```
Release(e) = NoRemainingPossibleWriters(e) AND
             (ProvablyNeverDispatched(e) OR QualifiedTerminalOrNeutralized(e))
```

`NoRemainingPossibleWriters` fences every worker/native continuation, queued callback, retry and follow-up using e's claim; no old process can later pass the pre-send CAS. A pre-reserved named successor step gets a new ordinal/claim only after Release(e), not a lingering right under e's claim. `ProvablyNeverDispatched` requires a locked cancellation before any may-have-been-sent marker and removal of all future send rights, not merely lack of an ACK. `QualifiedTerminalOrNeutralized` is retained provider/native evidence tied to this exact ordinal and scope which establishes either completion with no future application by that request, or terminal cancellation/neutralization of **all** its possible effects. It also identifies the actually installed finite residual path (or verified no remaining session path). Settlement CAS binds the observationSequence and cumulative consumed-credit count; if a newer observation committed first, recompute against that state before retiring anything. Unobserved natural progress after the sample is still conservatively covered by the sampled residual, never recredited as already observed history. No predicate is satisfied by End acceptance, stopped worker, claim deadline, new epoch/secret/room, a confirmation tap, HTTP timeout or any number of fresh snapshots alone. Explicit **Reconcile** gathers this evidence and displays pending/refused; it cannot waive the predicate. Neutralization that itself sends a write is not a workaround: it must be a qualified provider cancellation primitive applicable to the old request, not a fresh pause/play raced against it.

Use this one predicate for ordinary follow-up dispatch, reservation retirement, cleanup dispatch, output-owner handoff and guard removal. An **initialized idle** lane can dispatch its first operation only with the initialization proof below, current scope authority and no intersecting unsettled guard. A missing row is uninitialized, not idle. Completed effects have no ongoing writer, but their **installed automatic tail stays reserved** until observed/pass-through or qualified replacement/terminal cleanup proves it cannot run. Thus releasing a call's uncertainty is distinct from discarding the still-applied path. A cleanup is a new effect in that lane: fence future room work, Release every predecessor, freshly verify captured ownership, dispatch at most one qualified cleanup step, Release that step before another step or new owner. Never pause/delete/restore options on a different context to make End look successful. A cleanup marker is itself quarantined on ambiguous send.


**Shared execution gate, including existing revocation cleanup.** Merely adding a V2 guard table is insufficient. Every cooperating provider writer able to affect its captured output must consult the same guard/lane at pre-send: session V1/V2 broker queue/transport, connection `closeConnection` cleanup dispatched by `flushSpotifyCleanup`, reconnect/adoption, option restoration, native owned/solo/recap handoff and account-change cleanup. Carry original connection lineage/scope into these jobs; a post-commit job cannot infer permission from a new owner/secret. Existing raw cleanup dispatch is not Release evidence. V2 capability enablement requires these named shared entry points wired to guard-aware admission plus a qualified writer-generation fence; otherwise V2 stays off. V1 wire schemas/consumers remain strict and their ordinary behavior is preserved only on proved independent scopes; legacy uncertainty cannot opt out just because there is no V2 room. This shared gate/initialization boundary is an explicit exception to runtime byte identity, not authorization for a V1 redesign. A legacy route refused by quarantine or uninitialized scope returns its compatible unavailable/conflict outcome rather than sending the call. Root must assign the shared broker/auth/native ownership changes to one owner later.

## Queue fairness, history, reactions and presentation

Fairness policy: a turn is one confirmed observed visit, including intentional replays/restarts, not an accepted queue item or skipped/unobserved pick. Track observed turn counts per contributor. End-add while Take turns is on gets an automatic slot; rank each contributor’s pending automatic items by `(observedTurns + pendingOrdinal, firstJoinOrdinal, acceptanceSeq)`. This puts a new pick after pending picks with fewer projected turns and interleaves contributors; acceptance sequence serializes simultaneous commands under the room lock. Preserve contributor acceptance order. Recompute the automatic subsequence after add/remove/observed-start; removing or skipping before observation earns no turn. Current and played items never reorder.

Play Next inserts at the head of upcoming (latest accepted wins) and pins it. Drag pins the moved item at its chosen upcoming index; subsequent fair recomputation fills only automatic slots, so explicit overrides persist until that item is played/removed/moved. Toggle off freezes current order; all old automatic entries become fixed. Toggle on leaves existing entries fixed and applies to subsequent End adds only; no surprise reshuffle. Moving someone else’s pick does not change its contributor/turn credit. This is a chosen engineering resolution of P38, not an owner question.

Executable Python specification and worked examples (pure reference, no runtime implementation):

```python
# Slots: (pick_id, contributor, acceptance_seq, automatic)
def fair(slots, turns, joins):
    pending = {}
    ranked = []
    for item in sorted((s for s in slots if s[3]), key=lambda s: s[2]):
        who = item[1]
        pending[who] = pending.get(who, 0) + 1
        ranked.append(((turns.get(who, 0) + pending[who], joins[who], item[2]), item))
    ordered = iter(item for _, item in sorted(ranked))
    return [next(ordered) if item[3] else item for item in slots]
def ids(slots): return [s[0] for s in slots]
def pick(n, who, seq, auto=True): return (n, who, seq, auto)
j = {'A': 0, 'B': 1, 'C': 2}
a1, a2 = pick('A1','A',1), pick('A2','A',2)
b1, b2 = pick('B1','B',3), pick('B2','B',4)
assert ids(fair([a1,a2,b1,b2], {}, j)) == ['A1','B1','A2','B2']
# Off: append as accepted, no fair() call.
assert ids([a1,a2,b1]) == ['A1','A2','B1']
# A has two observed turns: B's first and second precede A's third.
assert ids(fair([a1,b1,b2], {'A':2}, j)) == ['B1','B2','A1']
# Concurrent C/B accepts serialize by seq; fewer-turn tie uses join order.
c1 = pick('C1','C',5)
assert ids(fair([c1,b1], {}, j)) == ['B1','C1']
# Remove B1 before observation: B2 becomes B's first pending turn.
assert ids(fair([a1,a2,b2], {}, j)) == ['A1','B2','A2']
# A1 was actually observed (one turn); remaining B1 now precedes A2.
assert ids(fair([a2,b1], {'A':1}, j)) == ['B1','A2']
# A1 skipped without observation earns no turn; tie still goes to A.
assert ids(fair([a2,b1], {}, j)) == ['A2','B1']
# Play Next and drag pin exact slots, automatic subsequence alone changes.
x = pick('NEXT','C',6,False)
assert ids(fair([x,a1,a2,b1], {}, j)) == ['NEXT','A1','B1','A2']
y = pick('DRAG','C',7,False)
assert ids(fair([a1,y,a2,b1], {}, j)) == ['A1','DRAG','B1','A2']
# Toggle off/on freezes old items; only new automatic items can be ranked.
frozen = [(*item[:3], False) for item in [a1,a2,b1]]
assert ids(fair(frozen+[b2], {}, j)) == ['A1','A2','B1','B2']
```

### Fungible capacity credits, observed ancestry and bounded storage

R2's200-visit bound failed when an already-applied natural next needed201 or a promised inverse/restored tail needed more space; refusing only a new control could not fix it. R3's predecessor-specific future UUID union is withdrawn. **Only a confirmed exact observation allocates an actual immutable visit UUID.** A planned finite vector contains occurrence references/order and an integer capacity budget, never future visit IDs or navigation edges. Keep <=512 compact **actual observed** records, append-only until recap erasure; their ordinal slots never recycle. Reserve maximum final bytes, visit-transition event allowance and terminal execution/receipt space for every credit before accepting any potentially visit-producing work. Occurrences remain <=100 lifetime, including removed/adopted/replayed entries. This is a design envelope, not a measured encoder/provider claim.

**Allowed provider continuations.** An enabled plan application has one audible cutover, no repeated republishing/retry/refill, repeat/shuffle/autoplay off and finite exact mapping. For old residual vector O and candidate vector N, every admitted continuation is an order-preserving old prefix (possibly all O, even after a long delay) followed by an order-preserving suffix/subsequence of N (possibly all N or empty), with at most one splice. Already-current preservation adds no visit; any qualified operation that can explicitly start/restart a target includes that target in N. A queue edit must preserve current recording/position/playing; its conservative N allowance may include the current item even though an unintended restart would be a product failure. O includes every old not-yet-observed start still possible at dispatch. This admits **old A-B-C-D -> candidate A-C-B-D -> old B -> new D** and the upcoming-only **A-B-C-B** hybrid. Identity/order qualification must map each observed occurrence exactly, including repeats; capacity never depends on predecessor identity. No detach or history exclusion is allowed to conceal an admitted hybrid.

The single-splice profile is a capability condition, not an assertion about arbitrary Spotify API behavior. A primitive allowing unqualified repeated old/new alternation/refill, unknown extra starts or unbounded repeat has no admitted finite budget under this model and is refused **before dispatch**. A multi-call operation is decomposed into immutable steps, each waiting for Release of its predecessor; if multiple steps can independently reinstall a finite path, reserve the sum of their target+tail lengths before the operation is accepted. Bound the step count/role vectors in the 32 KiB executor slice. Never count merely accepted noops as writes. Pause/resume/same-item seek profiles may use N=0 only when qualified not to introduce another start/reinstall/repeat; their existing automatic tail remains reserved. If that cannot hold, disable that case or reserve its full possible finite path before acceptance. No call that might add visits is exempt just because its UI label says Pause or cleanup.

**Union-free escrow.** C is actual observed record count. E is an active traversal escrow: remaining integer credits for the still-applied residual plus every dispatched but unsettled step's full possible finite continuation, less exactly observed new starts since the escrow was created/expanded. I reserves an unaccepted promised inverse target+**entire restored automatic tail**. D reserves the latest accepted **never-dispatched** desired queue candidate, including any cutover target allowance. Other accepted never-dispatched steps have separate budgets until merged into E. All are scalar operation budgets; equal recordings, common prefixes and duplicate occurrence references save **no** credits. An untouched I/D cannot fund E's observations.

```
C + E.remaining + I + D + other_accepted_budgets <= 512
reserved maximum visit bytes = 192 * (C + all remaining credits)
committed_semantic + reserved_visit_transition + reserved_terminal <= 20000
```

At a stable point E starts at |O|, counting only remaining starts, not the already-recorded current visit. Before a cutover claim, merge its full N budget into E while preserving the old remainder; E starts this interval with at least |O|+|N|. Each exact new observed start consumes one E credit, creates one fresh UUID/record, and reserves-to-committed transfers its visit-event/byte allowance. Same-visit progress and duplicate observation IDs consume nothing. Which planned predecessor or which semantic branch caused that start is **irrelevant** to allocation. If exact item/occurrence/start identity is ambiguous, keep diagnostic observations and mark unconfirmed rather than guessing. Uncertain **causality alone never suppresses an exact observed visit**: record it with unknown/requested-not-proven cause, including every admitted hybrid. Missing observations consume no history credit and earn no turn.

**Conservative bound.** For any one-cutover continuation, observed starts n <= actual traversed starts <= |O|+|N|; skips/gaps only reduce n. The cutover may arrive after O fully ends and then run all N: that worst case is already included, with no assumed settlement time. Until Release and exact installed residual R are established, retain E.remaining = |O|+|N|-n; do not free old credits because a snapshot currently looks like N. At qualified settlement, all old writers are excluded and R is finite; n+|R| <= |O|+|N|, so atomically replace E.remaining with |R| and release only the surplus. If the evidence cannot establish this inequality/residual, remain quarantined, do not dispatch. On later inverse/cutover, add its independently reserved full path and apply the same inequality. Induction over sequential settled steps proves arbitrary accepted Back/Undo/edits, without enumerating combinations of predecessors. There can be no second uncertain writer: even an accepted inverse waits for predecessor Release. Keep all unsettled escrow/events/bytes after End and across owner changes in the output guard.

**Admission and coalescing.** Under guard/room locks, reserve the full new desired budget before accepting add/move/remove/fair reorder. Preserve E and any already-sent step. Replace only D proven never dispatched, atomically: remove its budget and add the new full candidate; failure rolls back queue/order/Undo/reservations. Claim of D versus replacement is a locked CAS, so exactly one wins. An intervening accepted future edit invalidates an unaccepted Undo promise and can release I only after atomically closing that promise; an accepted inverse is execution work, never released by expiry. Rebase at pre-call is allowed only for a provably never-dispatched candidate, recalculating its full bound; if it does not fit, leave current applied playback intact and refuse/supersede that desired revision. Rebase does not exclude advance after dispatch; E's |O|+|N| covers it. Queue acceptance is desired/pending until qualified live-order settlement, never playlist-storage ACK alone. An accepted removal that loses to natural start retains that actual history with already_started/superseded outcome. At capacity, automatic fairness retains the last admitted finite order; it cannot publish an unreserved reorder or stop admitted audio.

**Controls and Undo.** Before accepting Back/Next, reserve old E, forward target+tail F, and inverse target+frozen restored tail I. Do not deduplicate the forward/old/restore vectors even if they are equal. At dispatch merge F into E. On forward Release reconcile its actual residual before advertising applied/Undo. Undo lasts 8s from that qualified observed application. Inverse accepted at 7.999s moves I into an accepted budget (then E at dispatch); it keeps all allowances at/after 8s. Unaccepted I can release on expiry or semantic invalidation; ordinary progress does neither. Pause Undo uses zero extra visits only for an identity-preserving qualified profile; still reserve its execution/terminal receipts. If any forward/inverse/byte/event/execution allowance is missing, refuse before promising Undo. At C=511,E=1, natural observation commits visit512 without stopping/omitting it; at C=512,E=0 the finite tail ends normally. Same-visit pause/resume/seek can remain available with N=0 and independent terminal allowance; any new start/Back/replay needing credit refuses. Increasing capacity, deleting history or silently detaching an admitted hybrid is not a substitute for reservation.

**Observed navigation ancestry.** Each committed record has immutable `visitID`, `previousObservedVisitID` = last actually committed visit (null only for first), and `backPredecessorVisitID`, assigned **at observation commit** from observed records only. Natural/Next/start advance sets Back predecessor to the departing observed visit. Deliberate restart of current inherits departing Back predecessor; a confirmed Back to observed target H inherits H's Back predecessor, so repeated Back walks history instead of bouncing. A forward gap A-[unobserved B]-C creates C.previousObserved=A and C.backPredecessor=A; B gets neither UUID nor history/turn, and Back at C<=3s targets A. The resulting A visit's chronological previousObserved is C while its Back predecessor follows old A's observed predecessor. **Undo Back/Next restores the preimage's navigation ancestry**: freeze the preimage observed visit reference in the accepted control; at inverse observation allocate a new visit whose chronological predecessor is the last actually observed visit, but whose Back predecessor is that preimage visit's immutable Back predecessor. For Z→A→B, UndoNext creates A′ with `previousObservedVisitID=B` and `backPredecessorVisitID=Z`. Back at A′<=3s selects Z, not B; >3s restarts A′ and still inherits Z. This follows the existing Back/restart rule: Undo restores navigation position while chronological history truthfully records the excursion. It does not rewrite A/B, remove B's turn or collapse A′ into old A; the inverse's reserved new visit/turn and frozen restored automatic tail remain required. UndoPause stays on the same visit. Store compact immutable observed ordinals internally, resolve to stable UUIDs on wire; no reference ever points to a credit, planned occurrence slot or a recyclable staging slot. Reusing cancelled D budgets changes no history references. Known unobserved B passing is a gap diagnostic, not an invented Back node. Same-recording ambiguity stays unconfirmed; exact provider item identity, not this credit model, establishes which occurrence was observed.

**Bytes and events.** Versioned compact internal arrays (wire fields stay named): `[visitUUID, occurrenceSlot, previousObservedSlotOrNull, backPredecessorSlotOrNull, observedAtMS, startPositionMS, authorityEpoch, transitionRevision, executionOrdinal, kindCode, sixReactionCounters]`. Slots0..511 never recycle after commit; occurrences0..99; bounded safe integers/timestamps; position<=2^31-1, executionOrdinal<=1000, six counters<=10000. <=192 bytes per maximal encoded record including its slice framing, pre-reserved for credits too. UUIDs are generated only at commit. Occurrence metadata stored once, <=1024 encoded bytes/record including slice framing, exact IDs/display/artwork; oversize selections refuse, no truncation/substitution. Privacy-controlled names/assets stay in the member/profile slice, never immutable track metadata or visit arrays.

Disjoint room slices including framing: 100×1024=102400 occurrence; 512×192=98304 observed+credit envelope; 16384 member/admission/profile refs; 32768 plan/guard-ref/authority/active effects/scalar escrows; 4096 fixed cursors/summaries; 8192 dedicated End/terminal expansion. Total **262144 bytes**. Unused visit envelope is not borrowed. Photo bytes, receipts, events, output-guard ledger and privacy-controller registry are outside room JSON with separate limits below; do not claim the 256KiB is total storage. Each credit owns one visit-transition slot; <=512 such slots can ever commit. Unused reservations retire only under Release or never-dispatched cancellation/closed unaccepted promise. Committed history references never retire/recycle. Actual encoder/escaping/property/DB proofs remain implementation qualification.

def subsequences(xs):
    return [list(v) for k in range(len(xs)+1) for v in combinations(xs,k)]
def continuations(old,new):
    return [old[:i]+tail for i in range(len(old)+1) for tail in subsequences(new)]
class Credits:
    def __init__(self,c,old):
        self.c,self.e,self.d,self.i = c,len(old),0,0
        self.observed=[]; self.unsettled=False; self.actual=[]
        self.check()
    def check(self):
        assert self.c+self.e+self.d+self.i <= CAP
        assert min(self.e,self.d,self.i) >= 0

        self.d=n; self.check(); return True

        self.check()

### P47 ownership boundary for Play again and Start again

Both are explicit new intents; opening/reading a recap has no playback effect. Local playback ownership actor increments a durable local generation to capture current mode/room/output, validates entitlement/exact IDs, and obtains a server-issued **handoff ticket** binding current membership/host state, old output-guard revisions, intended provider/account/output, local generation, recap revision, intent command and expiry. Final server CAS rechecks these values, every still-active membership for this verified install and all intersecting guards before granting any new writer; any concurrent admission/leave/End/owner change advances the same server ownership generation. Guest admission itself fences local solo/recap writes and requires the native ownership actor to quiesce its own audio before committing guest mode; it never invokes a guest playback executor. Thus a stale handoff cannot race a new guest admission into audio. Native installs that grant only if the local generation still matches. Late responses/old callbacks are discarded, and an uninstalled grant is fenced/never-dispatched, not audio. Lost result is lookup of the same intent, never an automatic new start. No provider route (solo, practice/recap, new session, device picker, reconnect, other account) may bypass a captured-output guard. Playback changes outside participating Lyrica adapters cannot be prevented by this DB; they are external uncertainty, not delegated guest authority.

| State when explicitly tapped | Play again (local on this phone) | Start again (new room) |
| --- | --- | --- |
| Idle, no active membership/owner and no intersecting unsettled guard | CAS local generation + server handoff; exact provider recording list may start under local owner | Atomic ticketed create+seed under new host install, then explicit initial playback intent via the sole lane |
| Active guest (including pending leave) | First **Leave ACK committed on server**, revoke membership/capabilities, then local/server CAS and guard checks. No audio while still guest. Host room continues; a disjoint local output may play only after acknowledged leave | Same Leave ACK before create/host grant; membership lookup on retry resolves an ambiguous leave. Denied/delayed leave -> pending, no guest audio |
| Active original host | Explicit End intent first; End ACK fences new room work but is **not** cleanup completion. Wait for Release of every predecessor and cleanup step and verified old output disposition before handing off | Same End + Release + cleanup boundary, then atomic new create/seed and new authority; no transfer of old membership/OAuth/lease |
| Ended-clean | Recheck guard revisions/current owner; generation + server CAS grant | Same recheck; new ticket/new room; old recap data is only seed provenance |
| Ended-uncertain, cleanup pending/uncertain, or unknown current mode | Typed `pending_output_settlement` or `output_quarantined`; Reconcile collects Release evidence. No fresh local owner writes to intersecting scope | Same refusal/pending, even with new room UUID/secret/epoch or confirmation tap. No finite recovery promised for unsupported terminal evidence |
| Explicit different provider/account/device/output | First leave/end active role as above. Server verifies true scope disjointness; account-wide endpoint/unknown lineage/route overlap still intersects, including the original captured output. Switching account/provider strings is never proof of independence |

The handoff ticket grants no audio by itself and never carries broker secrets. Server/local ownership validation occurs again immediately before dispatch. A foreground Apple native guest cannot exploit the local Play again route; Spotify remains broker-only while a session owns its output. Start again seeds a new room but may stay not-started if the explicit playback intent cannot safely execute. New room creation with initialIntent=none cannot itself grant overlapping write authority; subsequent start still uses the guard.

Start again snapshots authorized source recap revision and all exact provider/storefront recordings, creates new invitations/members/lease/settings defaults and zero reactions/history, allocates occurrence IDs and stores ordered list or cryptographically generated shuffle permutation. Receipt stores seed/permutation so retry cannot reshuffle. Any unavailable exact recording or >100 source visits refuses the whole seed with unavailable list; no truncation/substitution. Any entitled historical participant may explicitly become new original host. Seeded contributions all attribute that new host; private source refs never copy old names/photos/consents into a new audience. Ordered uses observed visit order including repeats; shuffle permutes that multiset. Defaults Ask=true/Take turns=false. Private recaps persist until deletion; privacy control survives actual key moves as defined above. Host share requires explicit current public-name consent and can be revoked immediately; sharing conveys neither private photos, membership, returning trust nor restart entitlement.

def guest_persona(key):
    return dict(owner=('guest','G',key),key_owner='G',credential='C',
                expiry=EXPIRY,token_live=True,key_live=True,user_live=True,
                withdrawn=False,gen=0,pii=True)
def guest_live(p,t):
    return (not p['withdrawn'] and p['token_live'] and p['key_live'] and
            p['user_live'] and p['key_owner']=='G' and t<p['expiry'])
