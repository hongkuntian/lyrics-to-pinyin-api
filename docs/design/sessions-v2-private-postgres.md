## Intended coverage, not results

Six top-level scenario groups contain explicit ordering/cleanup controls:

1. **Approve versus deny, both winners.** Hold after the real receipt INSERT, observe a different backend blocked by the winner, then require discovery `conflict` without a hidden restart. An explicit fresh transaction uses the exact same losing intention. The terminal UUID, winner actor/requester provenance, member/lease, active grant or denial cooldown, events and coalesced wake remain unchanged; only the new loser's receipt is added. Exact retry/read thereafter is effect-free.
2. **Approve versus requester cancel, both winners.** The same barriers and explicit-intention resolution prove admission persists when cancel loses, and cancellation persists without membership/trust when approve loses. The historical lease is not a current membership grant.
3. **Other-participant credential invalidation wins.** A separate client updates the pending requester's actual `library_tokens.revoked` row and holds the transaction. The still-authenticated host blocks, then refuses `unauthorized` after revocation commits, with the complete V2 snapshot unchanged. A revoker-rollback control lets the waiting approval commit. An observer-failure control verifies unlock-before-drain cleanup.
4. **Command wins before other-participant invalidation.** Approval holds after actual room/grant/events/outbox/receipt writes. A separate credential revoker must wait on its real locks. Release, drain, then commit revocation; host auth remains live, but exact replay, saved receipt, altered-body conflict disclosure and requester read/cancel all refuse. The saved V2 rows remain retained and unchanged. A real-lock observer-failure control verifies mutation release and both outcomes drained before revoker rollback/release.
5. **Current actor versus historical lease.** Wrong captured Leave lease returns a durable conflict without closing membership; exact Leave closes lease 1 to 2 once. Its saved receipt remains readable while currently authorized. The retained admitted summary still says lease 1; a subsequent cancel cannot reopen membership, and new former-member decisions/Leave refuse. Host/unrelated requester lookups refuse. Revoking only that exact app session denies its saved reads/retries without pretending this bearer-only revocation withdraws another live audience's underlying guest credential/persona.
6. **Actual PostgreSQL guest deadline after writes.** A short, finite positive requester credential deadline is retained identically in the real token and persona rows. At the receipt barrier the provisional grant/member/terminal/events/wake/receipt must already exist and wall time must still be before expiry. A PostgreSQL sleep crosses that exact deadline; on the held client's real queries, transaction-start `now()` remains live while `clock_timestamp()` is expired. Final actual authorization must refuse and roll back every provisional V2 effect. Subsequent host mutation/read and requester access remain denied without any materialized persona withdrawal or cleanup job.

## Cleanup and failure ownership

The database wrapper borrows one actual client per transaction, gives it a unique application name/PID, commits immediately after the callback returns and rolls back/releases on failure. Setup/autocommit acquisition is tracked too; a failed migration's explicit transaction is rolled back before release. Defaults are 3-second connection/lock timeouts, 8-second statement timeout, 15-second idle-transaction timeout, a 2-second bounded lock observer and a 10-second failsafe mutation hold. These are unexecuted harness bounds, not latency evidence or product timeout changes.

Every entered/blocked/assertion failure is inside an ownership `try/finally`. Held mutation scopes release before draining their owned outcome promises. **Revocation-first** rolls back/releases its revoker before draining the command waiting for it. **Command-first** releases the mutation hold, drains command and revoker UPDATE, then rolls back/releases the revoker. Acquisition failure also rolls back/releases the just-borrowed client. Outcome rejection handlers attach immediately; no unobserved command promise is abandoned.

After each scenario, the suite checks no outstanding outcomes/holds/cleanup scopes/borrowers, no pool waiters, all pooled clients idle and no idle/aborted transaction in the exact test database. Final teardown first invokes any retained dependency-aware scopes and drains outcomes; it never calls `pool.end()` while an unaccounted borrower remains. Any cleanup assertion/failure is reported, not converted to success. The explicit observation-failure controls must establish that these checks actually hold on Root's eventual run.
