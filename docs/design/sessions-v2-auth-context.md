## Actual representation and adapter

Inspected `AppAuthStore.authenticate`, `credential`, `session`, `register`, `matchKey`, `authPolicy`; `AccountStore.guest/signIn/signOut/delete`; admin revocation; `SongLibraryStore.createUser`; Spotify revocation/store; both database wrappers; and actual migrations `001-song-library.sql`, `021-app-auth.sql`, `025-memberships.sql`.

Existing `authenticate(bearer)` returns exactly the useful auth tuple `{id,keyID,bundleID,credentialDigest}`. It **does not return the app-session digest**. The underlying session table has `digest,key_id,credential_digest,audience,expires_at,revoked`, with no issued-at column. Selecting a currently valid session by credential or key would authorize an expired/replaced bearer and is forbidden.

`createCurrentAuthContext({authStore,environment})` requires the actual trusted `AppAuthStore` instance with its `authenticate` method and validated `policy`. It imports only Node crypto and the existing V2 safe error class, avoiding the unrelated V1 dependency graph. Construction snapshots audience, attestation environment and bundle allowlist. The existing prefix shape is checked, without pretending to perform App Attest verification. Limits are a 64-character audience, 32 allowed bundles of at most 128 ASCII characters, the existing 10-character prefix and canonical base64 32-byte key IDs. The normalized deployment environment follows the V2 schema. Production requires production attestation; development/test/specific-preview requires development attestation and refuses the reserved `lyra-production` audience. Configuration is trusted, fixed per instance and never request-selected.

The frozen factory has three methods:

1. `prepare(bearer)` accepts the extracted normal session bearer string, never a header, guest/beta/Apple library credential, digest, user tuple or request-body identity. It applies the existing HTTP normal-session namespace and 256-character bound, calls `authStore.authenticate` with that exact string, and computes its SHA-256 server-side. The copied authenticated tuple and exact bearer digest live in a private WeakMap. The frozen result is `{principalID,keyID,bundleID,evidence}`, where `evidence` is an empty frozen opaque object. No raw bearer, credential digest or session digest is exposed by this result. It survives the receipt store's shallow `{...authentication}` copy. JSON reconstruction, a foreign factory handle or altered identities refuse. HTTP wiring must call this instead of constructing evidence from `req.lyricaUser` alone; a newly issued bearer requires new preparation.
2. `discover({tx,authentication,requiredScopes?})` resolves that exact session/user/token/key from the real public relations on the supplied active transaction. `requiredScopes` is a trusted, already collected union `{userIDs?:[],credentialDigests?:[],keyIDs?:[]}` for the operation's other dependencies. Each list is bounded to 64 input entries, validated, copied, deduplicated and sorted. Actual token/key owners are read and incorporated before any row locks; each final identity set also has a 64-entry cap. Missing extra token/key rows refuse. Discovery returns a frozen opaque plan with frozen `userIDs,credentialDigests,keyIDs` lists and environment. Private plan metadata retains the exact connection, database transaction ID and discovered identities. All reads are bounded primary-key/array lookups; there is no user/key/session enumeration or fallback.
3. `lock({tx,discovery})` consumes the original plan once on its exact connection and transaction. It obtains each sorted user row `FOR UPDATE`, each sorted token row `FOR UPDATE`, then **all** sorted exact App Attest key rows `FOR UPDATE`. The authenticated key is always included and supplies the receipt gateway's exclusive replay anchor across HMAC versions. It then locks the **exact bearer session** `FOR UPDATE`, before any connection/guard/persona/grant/room lock. This additional session lock also serializes direct session revocation/deletion that does not first touch the key. Owners/session bindings are compared with discovery while locking and again in the fresh auth query. A changed owner, token or key scope throws `conflict`; it never expands the plan or locks a newly found earlier row. Revocation/missing actor session/current-auth invalidity throws `unauthorized`. The caller must roll back and, where appropriate, begin a separately prepared bounded attempt; the primitive never retries.

The retained transaction identity is `pg_current_xact_id()::text`, an opaque PostgreSQL xid8, with no Number conversion. It is checked across discovery, locking and revalidation. Reused pool client objects can start new scopes in new transactions, while old plans/scopes fail there. Autocommit/pool-query facades fail before row locking when the transaction ID changes. This requires PostgreSQL support for `pg_current_xact_id()` (PostgreSQL 13+) and an actual same-client transaction; it creates no identity/auth table or permanent anchor. A failed attempt cannot rediscover on that same still-open transaction.

Applicable existing settings/admin/identity anchors must precede this discovery/lock phase. The trusted composer must collect all referenced identities before calling it. It cannot append a host/guest/controller key later from a locked room. Principal IDs retain exact opaque Unicode text, bounded to 128 JavaScript characters with no whitespace/control characters, matching the receipt identity boundary; they are never normalized, replaced or hash-substituted. All identity lists use lexicographic UTF-8 byte order, equivalent to SQL `COLLATE "C"`; cooperating writers must use the same order. The primitive does not inspect arbitrary SQL performed by the caller or certify that the caller has acquired those earlier anchors.

## Scope, liveness and time

`lock` returns a frozen **internal** scope:

```js
{
  environment, principalID, keyID, bundleID, audience, attestEnvironment,
  credentialDigest, accessKind,
  sessionExpiresAtMS, credentialExpiresAtMS, notAfterMS,
  revalidate: async ({tx}) => true
}
```

`credentialExpiresAtMS` may be null under existing authentication semantics. `notAfterMS` is exactly the minimum finite session/credential deadline. It is not extended by renewal or a default lifetime. Neither the scope nor its credential digest is a public DTO or a log payload. Raw tokens, public keys, attestation receipts and session digests are never returned. No request-provided timestamp or boolean proof is accepted.

Under the held rows, one same-connection SQL query revalidates exact session digest, exact key and credential linkage, token/key/user ownership, enabled user, all three revocation flags, session/key audiences, actual bundle and allowlist, actual App Attest environment, actual access kind and actual deadlines. Both initial locked authorization and revalidation sample `clock_timestamp()` in a materialized clock CTE; they do not use transaction-start `now()` or a client clock. Scope revalidation checks the connection and transaction, reads the already locked supplemental owners without expanding scopes, then performs the fresh auth query last. It takes no new row locks and performs no writes, scrubbing, renewal, provider calls or pool transactions. Changes to locked auth deadlines/access kind also refuse, including attempts to extend the frozen scope. Any thrown error must reach immediate transaction rollback; swallowing it cannot confer authority.

Timestamps are read as `floor(extract(epoch FROM timestamp)*1000)::text`. `decodeAuthTimeMS` checks canonical decimal text/BigInt range **before** Number conversion; safe integer Numbers are also supported, but already rounded unsafe Numbers refuse. Range is 0 through `9007199254740991`. Negative, fractional, malformed, nonfinite, infinity and int8-overflow values refuse as `unavailable`; null is permitted only for the existing nullable credential deadline. No JavaScript Date parsing participates. Flooring can refuse less than one millisecond early at a fractional expiry and never intentionally extends it. `nowMS >= notAfterMS` denies, including the exact deadline.

The scope linearizes at that SQL authorization point. Root's transaction wrapper must immediately commit after all required final checks, without network IO or arbitrary callbacks. As the receipt contract requires, its own final fresh DB-clock check must still cover time spent after revalidation. No application query proves the impossible property that a clock cannot cross a deadline during the subsequent COMMIT itself.

## Required composition: this is not lockAuthorization

The returned scope deliberately lacks `version`, persona/generation and `bindingKeyManifestHash`. It cannot satisfy the receipt gateway's permit validator by itself. Adding those fields with unconditional `true` checks would invent trusted authority and is forbidden.

Root must implement the complete hook around this primitive:

- Before lower locks, derive every action/result/receipt privacy reference and all its current controller, guest credential, user and key dependencies from trusted server state. Read-only discovery can inform the plan; recheck under the final held locks. Include the host-key grant anchor and every other required auth identity in the union. Missing/discovered earlier identities abort the transaction. If the complete operation exceeds this primitive's bounds, refuse; do not trim references.
- Acquire the applicable settings/admin/identity anchors, sorted users/tokens/keys (this primitive), exact session, sorted Spotify connections, output guards, personas, then host-grant scopes before handing off to the gateway's room/receipt locking. Other composers that lock sessions must use the same key-then-session position and deterministic session ordering if multiple sessions are involved. One actor session is implemented here; multi-actor bearer sessions are outside this API.
- Implement actual persona controller/generation and **GuestLive for every referenced participant**, current membership/lease and action rights, grant policy/generation and both grant sides, profile/resolve/consent authority, output quarantine and other action scopes. Supplemental locks here establish row exclusion/order only; they do not authenticate supplemental actors or validate their revocation/policy/privacy state. Different referenced actors may have different credentials/deadlines. Fold all actual dependency deadlines into the final receipt permit's minimum, and enforce them at every replay/new mutation/read/commit authorization point.
- Validate the supplied receipt-key manifest against immutable separately provisioned per-environment version/secret descriptors. The existing schema has no secret-fingerprint registry. This module neither compares nor echoes the manifest and provides no substitute attestation. Caller-supplied `manifestOK`/`privacyOK` flags would not establish this obligation.
- Compose read-only same-connection revalidation of **all** those scopes plus this scope's revalidation at the receipt phases. Saved results need current read/privacy entitlement before hash-conflict disclosure. Real failures must throw and roll back room/event/outbox/receipt changes together. The existing receipt store remains untouched.

This primitive follows actual ordinary app-auth semantics, including a nullable token expiry. That does **not** authorize unbounded guest retained data: Root's GuestLive/retention layer must bind its exact credential digest and finite actual deadline no later than 90 days. No credential family, guest credential extension, key-only erasure protocol, new principal or synthetic session is introduced. Fresh privacy.erase session age is a separate action requirement; the existing 15-minute issuance representation has no immutable issued-at field. This scope alone does not certify freshness age, historical privacy ownership, broker authority or consent.

## Existing writer limitations that keep V2 off

The existing schema expresses the current tuple and deadlines; no extra fields/anchors are needed for this bounded check. It does not itself enforce cooperative lock order, permanent no-resurrection, cross-pool database identity or lifetime hooks. Specifically, inspected existing paths require Root-owned changes before enablement:

| Existing writer | Observed limitation / required wiring |
| --- | --- |
| `AppAuthStore.session` | Reads the credential, takes a key lock, then replaces sessions. It must join the sorted user/token anchors before keys and recheck actual source auth/deadlines at the commit point. Preserve ordinary same-credential renewal without privacy withdrawal. |
| `AppAuthStore.register` / `challenge` | Registration lacks the shared user/token lock contract; challenge takes a user and performs global expiry cleanup, including sessions. Coordinate registration/first retention with invalidation, and qualify cleanup ordering with key/session locks and multiple keys. Do not lock an earlier key from inside a later session/room phase. |
| `AccountStore.signIn` | Takes membership settings/identity, invokes key-before-connection Spotify revocation, then moves a key, revokes the old credential and deletes sessions. Resolve source/target users and token/key union first. Move only live G/K history to A, withdraw shared-C dependencies for other guest keys, fence active authority and preserve guards in that same database transaction. A-to-B does not transfer A history. |
| `AccountStore.signOut` / `delete` | Revocation takes keys/connections before token/user updates and existing V1 scrub. Reorder all required auth scopes before Spotify/lower locks; wire immediate credential-loss privacy denial, bounded cleanup and controller-aware deletion without releasing output guards. |
| `app-auth/admin.disableUser`, `revokeKey`, `revokeSessions` | Disable uses settings/user/token/key, while key revocation starts at the key and direct session revocation may skip keys entirely. Enumerate the full bounded lock scope first, unify order with receipt/current-auth paths and wire V2 fencing/withdrawal in the transaction. The new exact-session lock covers direct session writes but does not repair all cross-feature deadlock orders. |
| `SongLibraryStore.createUser` | Revokes tokens then may un-revoke a reused digest. It lacks shared ordered token/key/persona invalidation and no-resurrection semantics. Prevent dependency resurrection before token reuse/expiry extension or user/key reenablement. Current liveness checks cannot recover a hidden revoke-and-reactivate history. |
| `revokeSpotifyInTransaction` / `SpotifyStore` writers | Preserve their existing keys-before-connections rule, but move the whole user/token/key union ahead of these calls. Existing signout/key/connection paths can otherwise invert this primitive's order. Reconcile scope discovery with shared cleanup/pre-send gates and legacy output initialization. |
| Account/library database wrappers and roles | Different configured URLs/pools are not proof of one authoritative database. Root must establish same-database/schema transaction wiring, appropriate SELECT/UPDATE row-lock privileges, bounded lock/statement/transaction deadlines and immediate rollback/commit. No second-pool/after-commit privacy hook is acceptable. |

Uncooperative writers can deadlock, alter earlier scope identities or reactivate dependencies. Database row locking and current-auth rechecks cannot manufacture the missing lifecycle history. The module stays unused/default off until Root qualifies these writers, the complete hook and shared execution gates. No enablement or full-auth/privacy qualification is claimed.
