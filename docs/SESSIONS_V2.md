The immutable [proposal](design/sessions-v2-architecture.md) has SHA-256 `7d4bd6a6d6b8b6c7be2044a2be61c0fd7841c1ba77d9e982bd592e7d1a24f049`. The [implementation sequence](design/sessions-v2-implementation-plan.md) distinguishes design approval from runtime qualification.

## Current boundary

The implemented foundations include server-only creation tickets, strict core command/recording validators, the approved Take turns ordering function, additive storage, atomic receipt transactions, bounded admission/member transitions, exact-bearer current-auth locking, an internal SQL admission service and a current privacy-authority composition. **No V2 HTTP route, capability, live room, migration runner, worker or provider operation is enabled.** Existing V1 runtime is unchanged. These are foundations, not Sessions parity or a deployed backend contract.

The [core wire contract](design/sessions-v2-wire-contract.md) covers seven room mutation shapes with immutable semantic hashes and exact recording tuples. The [fairness helper](design/sessions-v2-fairness.md) implements the approved automatic-slot reference through byte-bounded raw JSON and trusted server-domain Maps. The [storage foundation](design/sessions-v2-storage-schema.md) defines eight environment-scoped relations; migration 030 remains unregistered and unapplied to any live database. Its guard-only cleanup representation survives room deletion without widening account-role execution grants. The independently reviewed [receipt gateway](design/sessions-v2-receipt-store.md), [admission reducer](design/sessions-v2-admission.md) and [current-auth primitive](design/sessions-v2-auth-context.md) remain internal and unused. The internal [SQL admission service](design/sessions-v2-admission-store.md) atomically composes admission/member transitions with receipts, grants, compact terminal events and coalesced outbox work. The [private composition](design/sessions-v2-privacy-context.md) uses actual AppAuthStore/current-auth/receipt/admission code for approve/deny, requester cancel, guest Leave and currently authorized saved-result reads/retries. Unsupported actions refuse. Shared lifecycle hooks, permanent withdrawal/controller-transfer writers, End/room expiry, shared execution and actual adapters remain unfinished.

`api/utils/listening-v2/tickets.js` issues ten-minute HMAC-SHA256 tickets with server-allocated room/command UUIDs and a random nonce. The authenticated handler must derive the deployment, principal and verified App Attest key; callers cannot supply those authorities or choose expiry/UUIDs. Create and restart are separate intents; restart also binds the exact source recap revision.

The validated semantic intent hash excludes the creation ticket itself and the separately MAC-bound server UUIDs. It includes protocol/action, applicable expected revisions and payload. `canonicalCommandHash` accepts **raw JSON text only**, with a 16 KiB UTF-8 limit checked before parsing. Preparsed objects are refused: V8 can allocate their full key enumeration before a loop's width check. The future HTTP adapter must cap its input stream before accumulation; trusting `Content-Length` or serializing an already unbounded `req.body` does not establish that boundary. No HTTP adapter is added here.

Within that admission bound, object keys use lexical order (including numeric-looking keys); array order, exact integers and Unicode are preserved. Numeric tokens must use decimal integer syntax within the safe-integer range: no fraction or exponent notation, even `1.0` or `1e0`. A bounded scan outside quoted text validates every numeric token before parsing, including values that a later duplicate property would overwrite. JSON parsing remains responsible for complete syntax validation. Rounding/underflow cannot turn a fractional intent into an accepted integer. Hashing refuses nonobject roots, forbidden property names and excessive depth/nodes. It streams into the digest after cumulative encoded-byte checks, including key names, escapes and punctuation, and collects only a bounded key set before sorting. Hashing does not validate action rights or authorize execution.

`verify` is side-effect-free. It checks the signature, signing-key identity, exact context, fixed lifetime and server-clock validity before returning the immutable ticket payload. Unknown retired keys, altered bindings, future issuance and malformed encodings refuse; expiry returns `expired`. Verification does **not** consume a ticket or prevent replay by itself. The subsequent room/receipt transaction must enforce the reviewed unique keys, canonical-body conflict and current authorization/expiry checks. A lost result after expiry uses authenticated lookup; it never recreates the intent automatically.

Keys are server-only buffers with at least 256 bits of entropy, injected by the eventual runtime. Tests use fixed synthetic keys and clocks. No secret configuration is added in this checkpoint. Public errors expose stable codes without private state.

The private-composition production/hermetic inputs `d7a6aa8ff2b20b4d1776276462db2aa1438ac793` passed **725 unit, 686 integration and 21 contract tests (1,432 total)**, zero failures/skips, after a canonical dependency install. Security and operations independently approved the supported disabled subset; each executed its 26 composition cases once. Later changes add only the manual harness and documentation outside npm's hermetic globs; their unchanged production/hermetic inputs retain this gate.

The [private-admission PostgreSQL suite](design/sessions-v2-private-postgres.md) passed **16 Node tests in six top-level groups**, zero failures/skips, using actual private-composition code, default pg bigint decoding and synthetic owner-role identities. It exercises both admission winners, referenced-guest revocation orderings, current-authorized saved-result access, historical leases, after-writes wall-time expiry rollback, and unchanged sent/uncertain guards. Independent review found that the first observer-failure control could discard a revoker query error. An actual PostgreSQL cancellation exposed that loss; the corrected harness validates both outcomes and preserves unexpected errors alongside the observer sentinel. The owned Unix-only cluster is stopped after qualification.

These receipts do not establish deployed runtime/account roles or cross-pool identity, real enrollment, coordinated lifecycle/controller transfer/no-resurrection/scrubbing, initial room creation/request/profile/resolve flows, expiry workers/End, outbox delivery/load, provider Release or legacy-scope initialization, native behavior, HTTP/WAF/packaging or rollout readiness.
